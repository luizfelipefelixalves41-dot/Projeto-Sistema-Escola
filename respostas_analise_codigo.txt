5- A pesquisa de alunos por nome funciona com nomes completos, partes do nome e diferencas entre letras maiusculas e minusculas?

Resposta:
Sim. A pesquisa de alunos por nome funciona para nomes completos, partes do nome e diferencas entre letras maiusculas e minusculas.

No arquivo app.py, a rota de alunos pega o valor digitado no campo pesquisa, remove espacos extras com strip() e monta uma consulta usando LIKE com porcentagens antes e depois do termo pesquisado:

WHERE LOWER(a.nome) LIKE LOWER(%s)

O parametro enviado para a consulta fica no formato:

%termo_pesquisado%

Isso permite encontrar alunos mesmo quando o usuario digita apenas uma parte do nome. Por exemplo, ao pesquisar "Ana", o sistema pode encontrar "Ana Lima". Ao pesquisar "lima", tambem pode encontrar "Ana Lima", porque o LOWER() transforma tanto o nome salvo quanto o termo pesquisado para letras minusculas durante a comparacao.

Conclusao:
Sim, a pesquisa esta implementada de forma adequada para buscar por nome completo, parte do nome e sem diferenciar maiusculas de minusculas. Uma melhoria possivel seria tratar tambem diferencas de acentos, por exemplo permitir que uma busca por "Joao" encontre "Joao" e "Joao" com acentuacao, dependendo da forma como os nomes forem cadastrados e da configuracao do banco.


6- O fluxo de matricula impede que o mesmo aluno seja matriculado duas vezes na mesma disciplina?

Resposta:
Sim. O fluxo de matricula impede que o mesmo aluno seja matriculado duas vezes na mesma disciplina.

No arquivo app.py, antes de criar uma nova matricula, o sistema consulta se ja existe uma matricula com o mesmo aluno_id e disciplina_id. Se a matricula ja existir e estiver ativa, o sistema nao cria outro registro e mostra a mensagem:

"Este aluno ja esta matriculado nessa disciplina."

Se a matricula ja existir, mas estiver marcada como removida/inativa, o sistema nao cria uma duplicata. Ele apenas reativa a matricula existente, alterando o campo ativo para 1 e limpando o campo removido_em.

Alem disso, o banco de dados tambem possui uma restricao de unicidade para a combinacao aluno_id e disciplina_id. No MySQL, essa regra aparece como:

UNIQUE KEY uk_aluno_disciplina (aluno_id, disciplina_id)

No SQLite, a mesma protecao aparece como:

UNIQUE (aluno_id, disciplina_id)

Conclusao:
Sim, o sistema impede matriculas duplicadas do mesmo aluno na mesma disciplina. Essa protecao acontece tanto na logica da rota de matriculas quanto na estrutura do banco de dados. O comportamento tambem e adequado quando uma matricula removida e cadastrada novamente, pois o sistema reativa o registro antigo em vez de criar outro.


7- A remocao de matriculas esta funcionando conforme esperado, mantendo o historico no banco quando necessario?

Resposta:
Sim. A remocao de matriculas esta funcionando como uma remocao logica, mantendo o historico no banco de dados.

No arquivo app.py, a rota de exclusao de matricula nao apaga o registro da tabela. Em vez disso, ela executa um UPDATE na tabela matriculas, alterando o campo ativo para 0 e preenchendo o campo removido_em com a data e hora da remocao:

SET ativo = 0, removido_em = CURRENT_TIMESTAMP

Isso significa que a matricula deixa de aparecer como ativa na interface principal, mas continua salva no banco. A propria mensagem exibida ao usuario confirma esse comportamento:

"Matricula removida da interface. O registro continua no banco."

Na tela de matriculas, a listagem mostra apenas registros ativos, pois a consulta usa:

WHERE m.ativo = 1

Ja nos relatorios, o sistema busca as matriculas ativas e removidas, usando um campo de status que indica se a matricula esta "ativa" ou "removida". Assim, o historico pode aparecer nos relatorios mesmo quando a matricula nao aparece mais na tela principal.

Conclusao:
Sim, a remocao de matriculas esta funcionando conforme esperado para manter historico. O sistema nao exclui definitivamente a matricula; ele apenas marca como inativa e registra quando foi removida. Esse comportamento e adequado quando e necessario preservar historico academico. Uma melhoria possivel seria criar uma tela especifica para visualizar matriculas removidas, pois atualmente elas ficam preservadas no banco e nos relatorios, mas nao aparecem na listagem principal.


8- O metodo de remover dados do aluno em Aluno.py esta coerente com a regra de negocio definida para o projeto?

Resposta:
Parcialmente. O metodo remover_dados() da classe Aluno remove os vinculos do aluno com as disciplinas e depois limpa os dados do proprio aluno, deixando nome, CPF, matricula e curso como strings vazias. Ele tambem limpa a lista de disciplinas do aluno.

Esse comportamento faz sentido em uma versao simples e didatica do projeto, focada em orientacao a objetos, porque mostra como desfazer associacoes entre objetos em memoria.

Porem, quando comparado com a regra de negocio usada na parte web do sistema, o metodo nao esta totalmente coerente. No sistema web, a remocao de matriculas foi tratada como remocao logica: o registro nao e apagado do banco, apenas fica com ativo = 0 e removido_em preenchido. Isso preserva historico.

Ja o metodo remover_dados() apaga as informacoes do objeto Aluno em memoria, removendo dados importantes como CPF, matricula e curso. Em um sistema academico real, esses dados normalmente nao deveriam ser simplesmente apagados, pois fazem parte do historico do aluno.

Conclusao:
O metodo remover_dados() esta coerente com uma demonstracao simples de orientacao a objetos, mas nao esta totalmente coerente com a regra de negocio mais adequada para o projeto web, que valoriza a preservacao de historico. O ideal seria substituir essa ideia de "limpar dados" por uma remocao logica, como marcar o aluno como inativo, mantendo seus dados e seus registros historicos no sistema.

12- O banco MySQL pode ser criado corretamente a partir do arquivo schema.sql em um ambiente novo?

CREATE DATABASE IF NOT EXISTS sistema_academico

Em seguida, cria as tabelas principais do sistema:

- alunos
- professores
- disciplinas
- matriculas

13- O modo SQLite local funciona corretamente quando o MySQL nao esta disponivel?

Resposta:
Sim, pelo codigo o modo SQLite local foi implementado para funcionar quando o MySQL nao esta disponivel.

No arquivo db.py, o sistema primeiro tenta conectar ao MySQL usando as configuracoes definidas em DB_CONFIG. Se essa conexao falhar e a variavel MYSQL_REQUIRED nao estiver ativada, o sistema muda automaticamente para o modo SQLite:

_engine = "sqlite"

Nesse modo, o banco usado e o arquivo sistema_academico.sqlite3, ou outro caminho definido pela variavel SQLITE_PATH.

O codigo tambem cria automaticamente as tabelas no SQLite por meio da funcao _ensure_sqlite_schema(). Essa funcao cria as tabelas:

- alunos
- professores
- disciplinas
- matriculas

Ela tambem define restricoes importantes, como campos obrigatorios, campos unicos e chaves estrangeiras. Alem disso, ativa:

PRAGMA foreign_keys = ON

Isso e importante porque garante que o SQLite respeite as chaves estrangeiras.

O sistema tambem adapta as consultas para SQLite. A funcao _prepare_query() troca os marcadores %s por ?, que e o formato usado pelo SQLite. Alem disso, nas consultas com GROUP_CONCAT, o app.py usa uma versao diferente quando detecta SQLite, evitando incompatibilidade com a sintaxe do MySQL.

O README tambem informa esse comportamento, dizendo que, se o MySQL nao estiver instalado ou iniciado, a aplicacao usa automaticamente um banco SQLite local para permitir testar a interface.

Conclusao:
Sim, o modo SQLite local parece funcionar corretamente quando o MySQL nao esta disponivel. Ele cria o banco local, cria as tabelas, insere dados iniciais e adapta as consultas principais. A unica ressalva e que, para producao, o mais indicado e obrigar o uso do MySQL com MYSQL_REQUIRED=1, deixando o SQLite apenas como recurso de teste ou desenvolvimento.

19- O sistema possui configuracoes adequadas para uso fora do ambiente de desenvolvimento, como chave secreta e modo debug desativado?

Resposta:
Parcialmente. O projeto ja possui algumas configuracoes pensadas para uso fora do ambiente local, mas ainda nao esta totalmente adequado para producao.

Um ponto positivo e que a chave secreta do Flask pode ser configurada por variavel de ambiente:

app.secret_key = os.getenv("FLASK_SECRET_KEY", "sistema-academico-dev")

Isso permite definir uma chave segura fora do codigo. Porem, se a variavel FLASK_SECRET_KEY nao for definida, o sistema usa a chave padrao "sistema-academico-dev", que e adequada apenas para desenvolvimento. Em producao, uma chave fixa e previsivel nao e recomendada.

Outro ponto importante e que o arquivo app.py executa a aplicacao com:

app.run(debug=True)

Isso significa que o modo debug esta ativado quando o sistema e iniciado diretamente por esse arquivo. O modo debug nao deve ficar ativo em producao, pois pode expor informacoes internas da aplicacao e aumentar riscos de seguranca.

O projeto tambem usa variaveis de ambiente para configuracoes do banco, como:

- MYSQL_HOST
- MYSQL_PORT
- MYSQL_USER
- MYSQL_PASSWORD
- MYSQL_DATABASE
- MYSQL_REQUIRED

Isso e positivo, pois evita deixar todas as configuracoes fixas no codigo. A documentacao tambem orienta usar MYSQL_REQUIRED=1 em producao para obrigar o uso do MySQL e evitar depender do SQLite local.

O arquivo .gitignore tambem ajuda, pois ignora arquivos como .env, bancos SQLite locais e relatorios gerados.

Porem, ainda faltam alguns ajustes para producao:

- Desativar debug=True.
- Exigir FLASK_SECRET_KEY segura em producao.
- Usar um servidor WSGI adequado, como gunicorn, em vez de app.run().
- Garantir MYSQL_REQUIRED=1 fora do ambiente de desenvolvimento.
- Separar claramente configuracoes de desenvolvimento e producao.
- Evitar que o SQLite local seja usado acidentalmente em producao.

Conclusao:
O sistema tem uma base inicial para configuracoes fora do ambiente de desenvolvimento, principalmente por usar variaveis de ambiente. Mesmo assim, ainda nao esta totalmente adequado para producao, porque o modo debug esta ativado no app.py e existe uma chave secreta padrao de desenvolvimento. Antes de publicar, seria necessario desativar o debug, definir uma FLASK_SECRET_KEY segura e obrigar o uso do MySQL em producao.
